# Wearable ingestion upgrade — 19 October 2026

The old Withings webhook skipped any group lacking all fields required by the wide `vitals` row. The supported Withings measure mapping provides HR, SpO2, systolic/diastolic BP and now weight; it does not provide steps, sleep, active minutes or calories through this endpoint. The old complete-row path remains for compatible integrations, while partial groups now persist separately. No missing values are manufactured.

## Implemented contract

- `backend/models.py` and migration `20261019_0019_device_observations.py` add `device_observations` with patient scope, provider source/external ID, measured/received time, JSON supplied values, explicit missing fields and assessment state. The migration was applied to the local development PostgreSQL database on 19 October 2026.
- `backend/schemas.py` validates partial HR, SpO2, BP and weight bounds, requires at least one supplied measurement, normalises timezone-aware timestamps to UTC and checks BP order when both pressures exist.
- `backend/routes/integrations_withings.py` reads measurements from the authenticated provider API, rejects absent group IDs, unsupported extreme unit exponents and non-finite numbers, saves partial groups idempotently by provider group ID, and assesses observed critical values. An invalid group is logged and does not make a valid group disappear. Duplicate provider deliveries reuse the stored row. The connection records success when at least one valid complete or partial group is accepted; a no-valid-measurement attempt records an error.
- Malformed measure lists and non-object groups are handled without treating them as readings. A provider group with no measurement timestamp is rejected; the webhook window end is not substituted as a fabricated observation time. API date fields explicitly carry UTC offsets so the browser can display user-local times.
- `backend/early_warning.py` applies deterministic critical rules only to fields actually supplied. A partial HR of 150 bpm creates a review case without inventing BP/oxygen. `assessment_state` distinguishes `observed_fields_clear`, `deterministic_alert` and failed/unassessed states. It does **not** assert that absent fields are normal.
- `GET /integrations/withings/observations/{patient_id}` is server-side patient scoped. `frontend/src/app/pages/DevicesHub.tsx` shows partial values, absent fields, provenance and assessment state; the prior wide-reading view remains.
- Migration `20261019_0020_device_sync_attempts.py` adds one persistent attempt record per recognised webhook delivery, with pending/success/error state, completed time, newly accepted complete/partial groups, rejected groups and a bounded error code/message. `GET /integrations/withings/sync-history/{patient_id}` is patient scoped and returns at most 30 recent attempts. The device hub presents this history. Repeated deliveries remain separate attempts but do not duplicate stored observations; the repeated attempt has zero newly accepted groups. Failed attempts update `last_sync_at` while preserving `last_successful_sync`.

## Verification and limitations

Focused ingestion, adapter and early-warning tests passed, including sparse critical readings, duplicate identity, provider mapping, malformed units, repeated deliveries and patient-scoped history. Both local migrations passed. The full backend suite result and frontend checks are recorded separately in `REGRESSION_TESTING_REPORT.md`. The tests use synthetic provider responses and local SQLite/PostgreSQL; **real Withings OAuth/webhook delivery was not verified**. Historical attempts before migration 0020 are not backfilled. A process interruption may leave an attempt `pending`; the existing minute monitor marks attempts older than 30 minutes as `interrupted` without changing a later success or inventing a retry. That marker prompts investigation or provider redelivery. A malformed group without a valid measurement updates connection error state only when no other group succeeds; the history records rejection counts but not raw provider payloads or per-group reasons. Real-device coverage, provider retry timing and out-of-order delivery should be tested with authorised synthetic accounts before any production claim.
