## Verified change

Before this batch, `/ws/live/{patient_id}` checked a short-lived, patient-scoped ticket and patient access only at connection time. A connection could continue delivering live updates after a staff assignment was removed or an account was suspended. `backend/main.py` now reloads the user and patient scope from a fresh database session **before every outgoing update**, including periodic simulator updates. Revoked access closes the socket with policy code 1008. Removing the extra post-send sleep also bounds routine rechecking to the configured socket interval rather than two intervals. Database failure terminates the connection without sending the queued record. This does not claim exactly-once delivery or instant closure during an idle interval.

`backend/tests/test_security.py` now verifies active assignment, removal, suspension and role change against the live-socket check; verifies a queued update is withheld when the check fails; and tests the new device-observation API against another patient and role. The full security test file passed **28 tests** with one third-party Starlette deprecation warning. The complete backend suite passed **132 tests** with the same warning; see `REGRESSION_TESTING_REPORT.md`.

## Existing boundaries and residual risks

Patient-scoped routes use `get_accessible_patient` or scoped queries, returning 404 for inaccessible patient records. Admins cannot read clinical patient data through the central scope helper. The current security tests cover staff assignment removal, patient isolation, admin restrictions, notification receipt isolation, refresh rotation and replay rejection, MFA, AI pseudonymisation and several care workflows. They do not exhaust every route or WebSocket failure mode.

The React client stores access and refresh tokens in `sessionStorage`; this avoids persistence across normal browser sessions but makes tokens accessible to JavaScript executing in the page. Backend logout revokes the refresh session, while already issued access tokens remain valid until expiry (default 30 minutes) unless the account is suspended. A switch to HttpOnly cookies would need a paired CSRF design, deployment origin review and full authentication regression work; it was not attempted in this focused batch. WebSocket tickets expire after 60 seconds for connection establishment, but the current stateless ticket can be replayed within that window and is not bound to a refresh-session ID. Established sockets now recheck account and patient scope on delivery; logout alone does not immediately close a still-active socket. A future session-bound token/socket design should address this if immediate logout revocation is required.

Backend responses set CSP, no-sniff, frame denial, no-referrer and no-store headers; `frontend/vercel.json` configures CSP and HTTPS transport policy for the deployed SPA. Browser CSP still permits inline styles and broad HTTPS/WSS connections, so it should be tightened only after checking actual build assets, provider endpoints and deployment behaviour. The frontend has legacy `saveHealthData`/`loadHealthData` helpers that use `localStorage`, but a current source search found no callers; old browser-stored copies may remain on existing clients. Removing existing client data needs a deliberate migration/retention decision.

`npm.cmd audit` reported **zero** informational, low, moderate, high and critical findings in the installed frontend dependency tree on this date. A filename-only pattern search of backend/frontend source found no obvious private-key or common API-token literals. These checks do not replace a complete dependency, history or secret-management review. No real external AI request was made. The existing AI context pseudonymisation and consent logic warrant a separate adversarial prompt/source-validation batch.

The assistant's provider client is disabled unless AI is enabled, a key exists and governance checks pass. For non-synthetic classification those checks require recorded DPA, retention, regional-processing, audit and clinical-approval flags. Context retrieval is read-only, limited to recent records and pseudonymised in an existing test. This review did not prove that every provider response source ID and timestamp matches an authorised record. The audit endpoint is admin-only, but currently returns the entire audit table without pagination; no application audit-retention mechanism was found in the inspected route/configuration. Both need scale and retention decisions before live use.
